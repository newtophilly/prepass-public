# prepass on Agent Retrieval Bench

**2026-08-06.** 287 samples, 25 repositories, scored against seven published baselines
on a benchmark this project had no hand in building.

Every prior number in this repository comes from a harness written here. This one does not:
the samples, the corpus, the answer key, the metric and the baselines are all external.

## Summary

| task | n | prepass rank | prepass MRR | best other |
|---|---|---|---|---|
| trace2code | 101 | **1 of 8** | **0.574** | RepoMap 0.274 |
| comment2context | 80 | 4 of 8 | 0.225 | jina-code-0.5b 0.304 |
| code2test | 106 | 7 of 8 | 0.195 | Qwen3-Embedding-4B 0.322 |

prepass beats the published lexical baseline on all three: **2.8×**, **1.5×** and **3.0×** its
MRR respectively.

Total compute for all 287 queries: **19.2 seconds**, no index, no model, no network.

## The benchmark

Released 2026-06-09. Corpus of 345,776 files / ~7.0M chunks across 29 repositories; sample set
draws on 25. 150 of the 287 samples carry hand-picked hard negatives.

| task | question |
|---|---|
| `trace2code` | reproduced failure output → root-cause source files |
| `code2test` | PR intent / implementation change → related tests |
| `comment2context` | review comment + reviewed file → additional context |

## Fairness controls

1. **Their candidate set.** Files come from the benchmark's own corpus snapshots, materialised
   to a temp directory — not from repositories cloned here. prepass ranks exactly what their
   baselines ranked.
2. **Their answer key.** Gold is read from their published `*_details.jsonl`, keyed by
   `sample_id`. Verified: all seven baselines and prepass share identical sample ids, and all
   seven baselines share an identical gold set.
3. **The production code path.** Ranking calls `runHeuristicStage` from `dist/`, the same entry
   point the hook uses.
4. **Their metric.** Recall@k, because gold averages 1.45 files per sample. hit@k is reported
   alongside but is not the headline.

### The mistake this run made first

The initial run derived gold from each sample's `gold_blocks` field. That is a **subset** of
`gold_files` — it disagreed on **22 of 287 samples**, and every disagreement inflated recall.
The numbers were discarded before being reported.

The rule that follows: **never re-derive a label the benchmark already publishes.** The field
that looks correct may be a projection of the real one.

A stack trace is a dense list of exact identifiers printed verbatim by the failing program.
Rarity-weighted exact matching is the right tool, and dense retrieval blurs a signal that was
already clean.

Note that **prepass has no stack-trace handling**. Extracting paths from traces was evaluated
and killed (only 3 of 70 misses mentioned the target file anywhere); this result is plain BM25F
treating the trace as text. The negative result holds.

## The test-discount control

`code2test` is the **exact inversion of the SWE-bench artifact** documented in
[`git-history.mjs`](git-history.mjs) and `test-discount-2026-08-06.md`: a task where every
correct answer is a test file, built by other people for unrelated reasons.

That makes the artifact claim falsifiable for the first time. If `testWeight: 0.5` — the setting
worth +6 to +8 points of hit@1 on all three SWE-bench corpora — also helped here, then it was a
real improvement and the artifact story was wrong.

Same 106 samples, same corpus, same code, one config value:

| configuration | R@5 | R@10 | R@20 | MRR | hit@20 |
|---|---|---|---|---|---|
| **shipped** (`testWeight: 1.0`, off) | **0.250** | **0.378** | **0.498** | **0.195** | **56.6%** |
| SWE-bench-tuned (`testWeight: 0.5`) | 0.014 | 0.083 | 0.160 | 0.021 | 19.8% |

**MRR falls 9.3×. Recall@5 falls 18×.**

The falsification condition was stated before the run. It did not survive contact with a
benchmark whose answers are tests, which is exactly what an artifact should do.

`testWeight` stays at 1.0 and the config schema keeps documenting why.

## Caveats

- 287 samples over 25 repositories; per-task n is 101 / 106 / 80.
- Whole files were reconstructed from the benchmark's chunked corpus so a file-level ranker had
  files to rank. Baselines are labelled `candidate_filter: all_files`, but their internal
  chunking differs from this reconstruction. A real methodological difference, not a rounding
  error.
- trace2code draws on smaller repositories: median pool 126 files against ~1,430 for the other
  two tasks. Verified that pool size is repo-driven, not task-driven — the same repo yields the
  same pool across tasks — and every system faced the identical pool. The comparison holds; the
  absolute 0.777 should still be read against an easier haystack.
- **The classifier and the glossary were both switched off.** The harness passes a fixed
  `workload: 'search'` taxonomy and `glossary: {}` for all 287 samples, so intent classification
  never ran and no vocabulary bridging was applied. `search` is the wrong label for two of the
  three tasks. These results are the **ranker alone** — which makes the trace2code win harder,
  not softer, but nothing here measures those two components.
- prepass was run here, not by the benchmark's authors, and they have not reviewed these numbers.

## Reproduce

```bash
node bench/arb.mjs                      # all three tasks
node bench/arb.mjs --task trace2code    # one task
node bench/arb.mjs --limit 20           # smoke test
```

Point `ARB_ROOT` at an extracted Agent Retrieval Bench release. Calls no model, costs nothing.
